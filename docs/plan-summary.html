Seven calls that go against the brief

The brief asked me to argue when I disagree. These are the arguments. Each one is written up properly in the docs.

01
Removes an option

Stripe cannot be used

Stripe does not support South African registered entities for ZAR settlement or Connect payouts. If Rynet Digital is a South African company, Stripe is off the table no matter what the brief assumed. Peach Payments has native recurring billing and debit orders. Paystack has the cleaner API. My recommendation is neither in v1: invoice the first dealer cohort by hand and build billing once you know your plan structure.

02
Breaks the default stack

Vercel plus Neon cannot hit your TTFB budget

Vercel does have a Cape Town region. Neon and Supabase have no African region at all. So the default pairing puts your functions in Cape Town and your database in Frankfurt, roughly 170ms away, on a search page that issues several queries. Sub-500ms TTFB is not reachable that way. Vercel cpt1 with managed Postgres in AWS af-south-1, or a single VPS in the same region. Three options costed in the docs.

03

Not taking the newest TypeScript

TypeScript 7.0 is stable and roughly ten times faster. It also dropped lib/typescript.js, the compiler API Next needs, so Next 16.3 only supports it behind experimental.useTypeScriptCli, and typescript-eslint closed its 7.0 support request as not planned. 7.1 closes both gaps around October 2026. Pinning 5.9.3 with the revisit dated in writing.

04

Your brand red fails contrast twice

Not a problem, but it does mean the palette needs a real ramp rather than three hex values dropped into components. The measured numbers are in the next section. The short version: red-600 for link text, red-300 for accents on navy, and silver demoted to a dark-theme text colour and a light-theme decorative rule.

05

Poppins is wrong for the interface

It sets wide, reads slowly at 14px, and has no useful tabular figures, on a platform that is mostly prices, mileage, kilowatts and rates. Montserrat for display, because it is the logo's own voice. Inter for interface, tables and every numeral. Poppins kept for the agency site's large marketing type, where it looks good. I will build it your way if you disagree.

06

The dealer portal is not the Payload admin

A lead pipeline board, a feed mapping UI with dry-run preview, and drag-reorderable galleries make an application, not a content editor. Bending Payload's admin into that shape means fighting it on every screen. The portal gets its own route group and talks to Payload through the Local API, so the access control still applies without the admin shell.

07

SEO cannot be Phase 7

Server rendering, URL shape, canonical rules and structured data are decisions made while a template is built. Retrofitting them means rebuilding the template. SEO architecture moves into Phases 3 and 4. Phase 7 becomes sitemaps, redirects, Search Console and cutover, which is a real and much smaller phase.

Index control, borrowed from what already works here

Cars.co.za indexes exactly ten facet shapes and blocks everything else in robots.txt. That is a market-proven answer to the facet explosion problem, so we do the same thing deliberately, with our own shapes.

/cars all live stock /cars/[make] /cars/toyota /cars/[make]/[model] /cars/toyota/hilux <- model hub /cars/[make]/[model]/[variant] /cars/toyota/hilux/2-8-gd-6-raider /cars/in/[province] /cars/in/gauteng /cars/in/[province]/[city] /cars/in/gauteng/pretoria /cars/in/[province]/[city]/[make] and one level deeper for model /cars/body/[body-type] /cars/body/bakkie /cars/fuel/[fuel-type] /cars/fuel/diesel /cars/new /cars/demo /cars/used condition everything else is a query string, noindex follow: /cars/toyota/hilux?transmission=automatic&maxPrice=450000 /vehicles/[make]/[model]/[year]-[variant]-[ref] the listing itself /dealers/[slug] microsite /dealers/[slug]/branches/[branch] LocalBusiness, per branch /digital/services/[slug] agency, seven real pages

Three rules make it hold. Reserved slugs: in, body, fuel, new, demo, used, under and near are blocked on the makes collection, so a make can never collide with a route segment. Empty is not gone: a facet page with zero stock returns noindex and shows the nearest populated parent, rather than 404ing a URL that will have stock again next week. One page per query: /cars/toyota/hilux is both the search results and the model hub, because splitting those into two URLs is how sites cannibalise their own best keyword.

Index eligibility is one tested function, resolveIndexRules(), not meta tags scattered across templates.

The one hard rule, and how it actually holds

Only verified dealerships list. Never private sellers. Three layers, and the first is the one that matters.

LayerMechanismWhy this and not the obvious thing
Schema Consumers live in a separate auth collection, buyers. Staff and dealers live in users. A buyer has no role field and no dealer field, so there is nothing to escalate. The obvious thing, one collection with a role check, is one bad boolean away from being wrong.
API beforeValidate overwrites the dealer field with the session user's own dealer, discarding what the client sent. access.create requires verificationStatus: verified. That single overwrite is what stops dealer A posting stock under dealer B, and it is what the adversarial test suite aims at. Read access returns a Where clause, so the filtering happens inside the query rather than after it.
UI No sell-your-car route exists. No consumer listing form exists. /how-verification-works is a real page. The trust proposition is the whole product. If a buyer cannot find out what "verified" actually means, the badge is decoration.

Postgres row-level security was considered and rejected: Payload pools connections, so a session variable that sometimes fails to get set is worse than no fourth layer at all. The defence in depth is a test that authenticates as dealer A, tries to read and mutate dealer B, and asserts failure, for every scoped collection.

If there is a date, two levers actually move it. Ship the marketplace before the portal, onboarding the first dealer cohort by hand through the admin, which gets a live product with real stock months earlier and then builds the portal against real dealer behaviour. Or ship the agency site first of all: it is the smallest phase, it does not depend on the marketplace existing, and it is the only one that produces revenue on its own. I have assumed neither.

What I need from you

Sixteen questions in total. Four block the foundation and are marked. The rest can be answered as we go, but sooner is cheaper.

Blocking Where does the agency site live?

Marketplace on rynet.co.za with the agency at /digital, or the agency on digital.rynet.co.za, or a separate domain entirely?

Recommendation: subfolder. The marketplace will carry tens of thousands of URLs and is the only side of the business that builds real domain authority. A subfolder lets the agency inherit it; a subdomain is treated as a separate site and starts from zero. The cost is that the agency reads as subordinate to the marketplace, which may be exactly wrong commercially. That part is your call, not mine.
Blocking Hosting, and are you willing to pay for Cape Town?

Vercel Pro pinned to cpt1 with managed Postgres in AWS af-south-1 is the fast, low-ops answer and the most expensive. A single VPS in the same region with Docker is far cheaper and we own patching, backups, restore drills and PR previews. Vercel plus Neon is cheapest of the managed options and cannot meet the performance budget from here.

Recommendation: Vercel cpt1 plus af-south-1 Postgres. If the monthly cost is the blocker, the VPS is the right answer and I will build that path properly rather than half of it.
Blocking Does billing ship in v1?

Stripe is out, as above. Peach Payments has native recurring billing and debit orders. Paystack has the cleaner API and same-day payouts but is weaker on debit order, which matters for monthly dealer plans in this market.

Recommendation: no billing in v1. Your first dealers will be hand-signed anyway. Building billing before you know your plan structure is how you build the wrong billing. Peach in Phase 6.
Blocking Where does launch stock come from?

Do you have dealers signed? How many? Can you get me one real stock feed to build the import mapper against? If not, is v1 launching on seeded demo stock, and is that stock clearly labelled as a demonstration?

This one changes Phase 5 completely. South African DMS vendors have no common feed format, so building an importer against an imagined schema guarantees rework. One real feed is worth more to me than any spec.
Shapes the build Dealer verification: what do we actually check?

My assumption is CIPC registration number, VAT number where applicable, motor trade number, proof of business address, and RMI, NADA or MIWA membership where held, with a named human making the decision and the decision recorded in an audit trail. Confirm or correct. The entire product argument rests on this being real rather than a checkbox.

Shapes the build Finance calculator: whose numbers are we quoting?

Our own estimate with a disclaimer, or a real finance partner whose rates we quote? Very different compliance profiles under the National Credit Act.

Default assumption: our own estimate, clearly labelled an estimate, prime plus a configurable offset, total cost of credit shown, and a disclaimer field that is required and marked "requires legal review" until a qualified human has seen it. Prime is 10.5 percent on a 7.00 repo, effective 28 May 2026, and it lives in the CMS so an admin updates it the day it moves.
Shapes the build Reviews, ratings, WhatsApp, Afrikaans, trade-in data

Reviews. Collect our own, import Google, or ship without? Never mark up a rating we have not earned, so no source means no aggregateRating at all. My default: collect our own, verified against a real lead, show nothing until a dealer has five.

WhatsApp. A wa.me deep link is free and works today. The Business API gives templated messages and lead routing into the portal inbox, and costs per conversation plus Meta verification. Default: deep link in v1.

Afrikaans. Structure is scaffolded either way and costs nothing now. Real content at launch means translating every string, taxonomy label and legal page. If it is coming within a year, tell me now.

Trade-in. A licensed data source such as TransUnion or Lightstone is a real product feature and a real licence fee. A lead-capture form producing a range and handing to the dealer is honest and free. Which?

Confirm and I proceed Analytics, email, pricing, legal, timeline

Analytics: Plausible, which needs no consent banner because it collects no personal data, plus our own server-side lead event log. GA4 would sit behind the POPIA gate and lose most of its data to refusals.

Email: Resend sending from rynet.co.za, which needs SPF, DKIM and DMARC. Who controls that DNS?

Agency pricing: public tiers convert warmer traffic and filter better. A qualification path protects margin and suits dealer groups. I would publish a starting-from figure and gate the rest.

Legal: privacy, terms, POPIA notice, cookie policy, credit disclaimer and the dealer agreement all need a South African lawyer. I will write plain-language drafts marked "requires legal review" so they are cheap to review. Do you have someone?

Timeline: is there a date, or a date by which you need something live to show dealers?
