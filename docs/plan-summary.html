What cPanel cost, honestly

It is the right call for where this business is today. It is not free, and I would rather name the price than discover it in Phase 3.

01

SQLite, not Postgres

Your cPanel's PostgreSQL is version 10, from 2017 and long out of support, which Payload 3 does not accept. Payload supports Postgres, SQLite and MongoDB, and not MySQL or MariaDB, so the host's MariaDB is out too. That leaves SQLite, the same as Amico and Verboten, with the adapter switching on the connection string so a later move is a config change rather than a rewrite.

02
The ceiling, named

Amico is one dealership. This is a marketplace.

SQLite serialises writes, and Rynet has many dealers writing at once. It will be fine at launch and it has a ceiling. The trigger to move is written down rather than left to feel: SQLITE_BUSY appearing under normal load, or roughly 25 dealers actively managing stock, or p95 search above 300ms. Then it is managed Postgres in AWS af-south-1, which is in the same country as your host.

03

Three things become mandatory

Nothing writes on the read path, so view counters buffer in memory and flush by cron instead of writing per page view. Feed imports run chunked through a queue rather than as one long transaction that blocks every other writer. And no hand-written SQL uses SQLite-only syntax, because the Postgres move is a when rather than an if.

04

No PostGIS, no trigram

Radius search becomes an R-tree bounding box plus an exact haversine filter, which is precisely MotoHubSA's geo.ts. That file just moved from optional reuse to load-bearing. Fuzzy text becomes FTS5 prefix search, which costs less than it sounds because the typeahead does its real work in a deterministic parser rather than in the fuzzy match.

05
A real gap against the brief

No per-pull-request preview deployments

The brief asks for them and this host cannot do them. The substitutes are CI building and testing every pull request against a local production build, including axe and Lighthouse, plus a staging Node app on a subdomain running the same bundle. That is thinner than preview URLs and I would rather say so than let it pass unmentioned.

06

Node 22 and npm, not 24 and pnpm

Your cPanel offers Node 20 or 22, and Next 16 needs 20.9 or above, so 22. Pinning Node 24 because it is the current LTS would be pinning a fiction. And cPanel's Setup Node.js App runs npm install from its own button, so npm it is: a lockfile the host cannot read is worse than a slower install.

07

Media still goes to Cloudflare R2

This one does not bend. Amico keeps photos on the cPanel disk, which is right for one dealership with 97 cars. Twenty images per listing across 300 seed vehicles is 6 000 files before a single real dealer signs, and shared hosting caps inodes long before disk. R2 also leaves the cPanel disk holding one thing that matters, rynet.db, which makes the restore drill genuinely simple.

08

PayFast holds up, with one caveat

It does support recurring billing, through Subscriptions and through Tokenisation for ad-hoc amounts, with an API to update, pause, cancel and query. Verboten's signature generation and ITN notify route port across. The caveat: PayFast recurring is credit card only, no debit order, and some dealer principals will want a debit order for a monthly plan.

Two questions to your host, and they block Phase 1

Both take one support ticket. I cannot check either from here, and both are load-bearing enough that guessing would be irresponsible.

QuestionWhy it decides somethingIf the answer is bad
Is the home directory on local disk or NFS? SQLite's file locking is safe on local disk and unsafe on NFS. Almost every cPanel host uses local disk, but "almost every" is not a good enough basis for the single file holding every dealer's stock. SQLite is off the table entirely and we need managed Postgres in af-south-1, which changes the cost picture.
Does Passenger run one Node process or several? Several processes writing one SQLite file is fine in WAL mode on local disk. It also makes the in-memory caches and the counter buffer per-process. Not bad, just different: the counter flush and the Next cache tag invalidation both have to be designed for it, and I need to know before rather than after.
Two smaller ones for the same ticket What is the disk quota and the inode limit on the account? And has the host's PostgreSQL moved off version 10 since Amico went up? If Postgres is now 14 or later, SQLite becomes optional rather than forced, and I would want to reconsider.

Still arguing with the brief on four points

The brief said to argue when I disagree, so these stand until you overrule them.

01

Not taking the newest TypeScript

7.0 is stable and roughly ten times faster. It also dropped lib/typescript.js, the compiler API Next needs, so Next 16.3 only supports it behind experimental.useTypeScriptCli, and typescript-eslint closed its support request as not planned. 7.1 closes both gaps around October 2026. Pinning 5.9.3 with the revisit dated in writing. On this host the build only runs locally, so a build failure is a deploy that cannot happen.

02
Last design question standing

Poppins is wrong for the interface

It sets wide, reads slowly at 14px, and has no useful tabular figures, on a platform that is mostly prices, mileage and rates. Montserrat for display, because it is the logo's own voice. Inter for interface, tables and every numeral. Poppins kept for the agency site's large marketing type, where it looks good. This one gates the component library in Phase 1b, so it needs an answer before the others.

03

The dealer portal is not the Payload admin

A lead pipeline board, a feed mapping UI with dry-run preview, and drag-reorderable galleries make an application, not a content editor. Bending Payload's admin into that shape means fighting it on every screen. Own route group, Payload Local API, so the access control still applies without the admin shell.

04

SEO cannot be Phase 7

Server rendering, URL shape, canonical rules and structured data are decisions made while a template is built. Retrofitting them means rebuilding the template. SEO architecture moves into Phases 3 and 4. Phase 7 becomes sitemaps, redirects, Search Console and cutover, which is a real and much smaller phase.

Index control, borrowed from what already works here

Cars.co.za indexes exactly ten facet shapes and blocks everything else in robots.txt. That is a market-proven answer to the facet explosion problem, so we do the same thing deliberately, with our own shapes.

/cars all live stock /cars/[make] /cars/toyota /cars/[make]/[model] /cars/toyota/hilux <- model hub /cars/[make]/[model]/[variant] /cars/toyota/hilux/2-8-gd-6-raider /cars/in/[province] /cars/in/gauteng /cars/in/[province]/[city] /cars/in/gauteng/pretoria /cars/in/[province]/[city]/[make] and one level deeper for model /cars/body/[body-type] /cars/body/bakkie /cars/fuel/[fuel-type] /cars/fuel/diesel /cars/new /cars/demo /cars/used condition everything else is a query string, noindex follow: /cars/toyota/hilux?transmission=automatic&maxPrice=450000 /vehicles/[make]/[model]/[year]-[variant]-[ref] the listing itself /dealers/[slug] microsite /dealers/[slug]/branches/[branch] LocalBusiness, per branch /digital/services/[slug] agency, seven real pages

Three rules make it hold. Reserved slugs: in, body, fuel, new, demo, used, under and near are blocked on the makes collection, so a make can never collide with a route segment. Empty is not gone: a facet page with zero stock returns noindex and shows the nearest populated parent, rather than 404ing a URL that will have stock again next week. One page per query: /cars/toyota/hilux is both the search results and the model hub, because splitting those into two URLs is how sites cannibalise their own best keyword.

Index eligibility is one tested function, resolveIndexRules(), not meta tags scattered across templates.

The one hard rule, and how it actually holds

Only verified dealerships list. Never private sellers. Three layers, and the first is the one that matters.

LayerMechanismWhy this and not the obvious thing
Schema Consumers live in a separate auth collection, buyers. Staff and dealers live in users. A buyer has no role field and no dealer field, so there is nothing to escalate. The obvious thing, one collection with a role check, is one bad boolean away from being wrong.
API beforeValidate overwrites the dealer field with the session user's own dealer, discarding what the client sent. access.create requires verificationStatus: verified. That single overwrite is what stops dealer A posting stock under dealer B, and it is what the adversarial test suite aims at. Read access returns a Where clause, so filtering happens inside the query rather than after it.
UI No sell-your-car route exists. No consumer listing form exists. /how-verification-works is a real page. The trust proposition is the whole product. If a buyer cannot find out what "verified" actually means, the badge is decoration.

Row-level security in the database was considered and rejected on both engines: SQLite has none, and on Postgres a session variable that sometimes fails to get set is worse than no fourth layer at all. The defence in depth is a test that authenticates as dealer A, tries to read and mutate dealer B, and asserts failure, for every scoped collection.

One sequencing argument. With no dealers signed, the constraint is no longer a launch date, it is that you need something to show a dealer principal before you can sign one. That argues for moving Phase 4, the agency site, ahead of the marketplace: it is the smallest phase, it does not depend on the marketplace existing, it is the only one that earns on its own, and it is what you send a dealer principal first. Then the marketplace on seeded stock as the demo, then the portal built against real dealer behaviour. I have not reordered anything yet.

Still open

Eighteen questions in the doc. Four are answered. Two go to your host. These are the ones that need you.

Gates 1bMontserrat and Inter, or Poppins throughout?

The only design question left. Montserrat for display is right either way, because it is the logo's own voice. The argument is about the interface face.

My case for Inter: Poppins sets wide, which costs horizontal space in a filter rail you do not have to spare. It reads slowly at 14px in a spec table or a lead pipeline. And it has no useful tabular figures, on a platform where prices, mileage, kilowatts, instalments and rates all need to align in columns. Poppins stays for the agency site's large marketing type, where it looks good. Say the word and I build it your way instead.
Needed to seedWhat are the dealer plans, and what do they cost?

Now that billing ships in v1 I need the real structure: how many tiers, what each costs per month, the listing limit on each, and what the higher tiers unlock. Microsite theming, extra branches, extra users, placement in search.

I can build the plan machinery without this. I cannot seed it, and a demo with invented prices on the pricing page is exactly the sort of thing that gets quoted back at you by a dealer principal.
Shapes the buildDealer verification: what do we actually check?

My assumption is CIPC registration number, VAT number where applicable, motor trade number, proof of business address, and RMI, NADA or MIWA membership where held, with a named human making the decision and the decision recorded in an audit trail. Confirm or correct. The entire product argument rests on this being real rather than a checkbox.

Shapes the buildFinance calculator: whose numbers are we quoting?

Our own estimate with a disclaimer, or a real finance partner whose rates we quote? Very different compliance profiles under the National Credit Act.

Default assumption: our own estimate, clearly labelled an estimate, prime plus a configurable offset, total cost of credit shown, and a disclaimer field that is required and marked "requires legal review" until a qualified human has seen it. Prime is 10.5 percent on a 7.00 repo, effective 28 May 2026, and it lives in the CMS so an admin updates it the day it moves.
Shapes the buildReviews, WhatsApp, Afrikaans, trade-in data

Reviews. Collect our own, import Google, or ship without? Never mark up a rating we have not earned, so no source means no aggregateRating at all. Default: collect our own, verified against a real lead, show nothing until a dealer has five. On seeded demonstration dealers, no ratings whatsoever.

WhatsApp. A wa.me deep link is free and works today. The Business API gives templated messages and lead routing into the portal inbox, and costs per conversation plus Meta verification. Default: deep link in v1.

Afrikaans. Structure is scaffolded either way and costs nothing now. Real content at launch means translating every string, taxonomy label and legal page. If it is coming within a year, tell me now.

Trade-in. A licensed data source such as TransUnion or Lightstone is a real product feature and a real licence fee. A lead-capture form producing a range and handing to the dealer is honest and free. Which?

Confirm onlyCloudflare, analytics, email, legal, pricing page

Cloudflare. I want the domain on it, for the CDN cache your host does not provide, plus WAF, rate limiting, Turnstile on public forms, and R2 for the photography. R2 is not optional at marketplace scale. Confirm you are happy to move DNS.

Analytics. Plausible, which needs no consent banner because it collects no personal data, plus our own server-side lead event log. GA4 would sit behind the POPIA gate and lose most of its data.

Email. cPanel SMTP through nodemailer, matching Amico and Verboten. Needs SPF, DKIM and DMARC on rynet.co.za. Who controls that DNS?

Agency pricing page. Public tiers convert warmer traffic and filter better. A qualification path protects margin and suits dealer groups. I would publish a starting-from figure and gate the rest.

Legal. Privacy, terms, POPIA notice, cookie policy, credit disclaimer and the dealer agreement all need a South African lawyer. I will write plain-language drafts marked "requires legal review" so they are cheap to review. Do you have someone?
